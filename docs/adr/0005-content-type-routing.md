# 类型路由取代全局来源顺序

---
Status: accepted
---

刮削来源的参与集与优先级由「内容类型 → 有序来源链」决定，配置项为 `content_routes`，中文写「类型路由」。抓取前先判定条目的内容类型，只沿该类型的链取数；链上顺序即字段优先级。全局来源白名单 `enabled_sources` 删除：默认启用集就是「出现在某条链里」，停用一个来源就是从每条链里删掉它。

## 考虑过的方案

- **全局顺序 + 每个来源声明自己支持的类型**：两处真值（顺序与类型），改一处忘了另一处就出现「链上有它但它不支持这个类型」。而且「某类型下没有可用来源」这件事无法表达，只能表现为静默无结果。
- **每字段独立优先级链**：Python 支持，配置面是 24 个来源 × 12 个字段。默认配置下它的行为等价于链顺序（`compile_priority(route, {})` 退化成整条 route），收益不抵配置成本。
- **保留 `enabled_sources` 并与路由并存**：同一个问题有两个答案，用户关掉一个来源后还要回答「它在链里为什么还在跑」。

## 后果

- 配置契约破坏性变更：旧的 `enabled_sources` 需要迁移，非空时按交集裁剪每条链。
- 空链在保存时被拒绝，而不是留到运行时才报「该类型没有可用来源」。
- 加一个来源要同时决定它进哪几条链，否则它不会被调用 —— 这是刻意的：没有默认参与，就没有意外的网络请求。
