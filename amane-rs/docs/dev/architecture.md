# 架构

> 只记录**为什么**这样划分以及**什么时候会失效**. 签名与字段去源码。

## crate 边界

| 路径 | 边界 | 不变量 |
|------|------|--------|
| `crates/core/` | 番号、条目、媒体库扫描、配置、持久化 | 不依赖传输层; 不引入 `utoipa`; 无全局可变状态 |
| `crates/crawlers/` | 来源契约 `Source`、能力声明、登记表 `Registry` | 无状态; HTTP 客户端与配置在构造期注入; 站点实现编译进二进制 |
| `crates/net/` | 出站 HTTP: 浏览器指纹、按 host 限速、被拒后轮换 | 不感知站点语义; 限速器先于客户端构造, 由类型签名保证 |
| `crates/runtime/` | 任务处理函数 (刮削、扫描、资源物化) | 依赖 core、crawlers 与 net; 只做编排与写库, 不实现解析与获取 |
| `crates/server/` | axum 路由、DTO、错误映射、OpenAPI | 不持有业务规则; 领域类型到 DTO 的转换只在此层 |
| `crates/desktop/` | Tauri 外壳 | 只做装配: 生成令牌、绑定端口 0、打开窗口指向内嵌服务 |
| `ui/` | Vue 3 前端 | 只经 HTTP 契约访问后端, 不读取本机文件或数据库 |

领域类型与传输 DTO 分开 (`amane_core::Metadata` 与 `server::dto::MetadataDto`): 新增接口字段不会波及内核, 内核对宿主形态无感知。

## 启动顺序

`Runtime::boot` 的顺序不可颠倒:

```
冷配置 → 创建数据目录 → 打开数据库 (含迁移) → 仓储 → 恢复遗留任务
       → 来源登记表 → 处理函数表 → 任务运行时 → 路由装配
```

- **迁移在仓储之前**: 仓储的第一条查询假设表已存在。
- **恢复遗留任务在启动出队循环之前**: 顺序颠倒会让上次进程遗留的任务一直停在运行中。
- **来源登记表与处理函数表在任务运行时之前**: 运行时按类型查表, 缺表会把任务判成「没有注册处理函数」。
- **出队与调度循环由进程入口启动, 不在 `Runtime::boot` 内启动**: 测试装配路由时不希望后台线程自行领取或派生任务。

## 列表与筛选

- 筛选条件集中在 `MetadataFilter`, 组合时取交集; 字段的新增只改这一处。
- `list` 与 `count` 共用 `push_conditions`, 两处条件不会漂移; 命中总数与列表始终同源, 翻到末页不会出现「总数还有但列表为空」。
- 来源筛选走 `source_snapshot` 的 `EXISTS` 子查询, 因此「该来源贡献过内容」与「该来源曾命中」是同一件事。
- 分类筛选走 `json_each(metadata.genres)` 的 `EXISTS` 子查询。分类是开放取值, 不做白名单校验: 写错一个字得到空列表, 而不是让整个筛选报错 —— 与类型、来源这两类封闭取值不同。
- 关键字用 `LIKE`, `%` 与 `_` 在拼模式前转义; 不转义时搜 `100%` 会命中全部条目。
- 取值域有界的筛选值 (类型、来源) 拒绝未知取值并返回 400, 不静默返回空列表 —— 否则拼错一个字母看起来就像没有数据。来源的判定在 `MetadataFilter::validate` 里, 已知集合由调用方给出; 错误码留在传输层。可选项由 `GET /api/filters` 从枚举与来源登记表给出, 界面不自行维护枚举。

## 锁定与人工修订

- 锁定以「番号条目 + 字段」为单位记录, 字段取自 `LockableField`; 演员名单不在其中, 它是整体替换的列表, 没有逐项修订的语义.
- 刮削写入走 `apply_scraped`: 在同一事务里读取锁、剔除锁定字段、写行、按字段合并来源. 分成多次读会让「加锁」与「刮削」交错时丢掉刚写入的人工值.
- 被锁定的字段以 `None` 参与 `COALESCE` 写入, 因此保留原值; 解锁后下一次刮削即可覆盖, 无需额外确认.
- 可锁字段的展示、取值、清空、修订与聚合方式都定义在 `FIELDS` 这一张描述表里; 逐字段视图、剔除锁定字段、手工修订的列清单、聚合与 `INSERT` 的列绑定都从表里读, 按字段的分派不再散落各处.
- `INSERT ... ON CONFLICT` 的列清单与绑定同出于表: 改一处不会让列顺序与绑定顺序错开.
- 手工修订 (`PATCH`) 会同时做两件事: 把字段来源记为 `manual`, 并给该字段加锁. 只记来源不加锁, 下一次刮削就会覆盖人工值, 与「手工值不被覆盖」的承诺矛盾.
- 海报字段锁定后跳过下载; 未锁定时下载所依据的是写入后的 `poster_url`, 而不是本次刮削返回的地址.
- 标签按名字去重 (`user_tag.name` 唯一), 移除关联时不留下无人引用的标签名.

## 持久化

- 写池固定单连接, 读池多连接, 两者指向同一库文件。SQLite 同一时刻只允许一个写者, 多写连接会退化为忙等。
- WAL 与 `synchronous = NORMAL`: 读不阻塞写, 进程崩溃可能丢最后若干事务, 但不损坏库。
- 迁移经 `sqlx::migrate!` 在启动期自动应用; `migrations/` 只新增文件, 已应用的迁移不修改。
- 时间列以 UTC 存储, 由 `chrono::DateTime<Utc>` 与 TEXT 互转。
- JSON 列经 `sqlx::types::Json` 读写, 类型分别是 `FieldSources` 与 `ScrapedMetadata`; 调用方拿不到裸字符串, 结构变化由编译器发现。内容损坏时解码报错并指出列名, 不静默当作空值。

## 资源

- `resource` 以远端地址为键去重; 文件名在取得标识后才确定, 因此先插入再回写。
- 写入磁盘失败时撤销登记, 避免库里留下没有文件的资源。
- 类型以文件头为准, 上游声明的 `content-type` 只作参考; 不一致时记录告警。
- 资源端点以标识取内容, 内容不可变, 因此返回长期缓存头。
- 海报与封面是两类资源, 各自有远端地址与本地资源标识: 竖版包装图与横版剧照在详情页占不同位置, 合成一张会让其中一处变形。下载流程相同, 由 `ImageKind` 区分登记到哪一列。
- 海报下载失败不改变任务终态: 条目已写入, 缺图是允许的降级, 详情页据此提示。
- 删除条目时资源按远端地址共享: 还有别的条目引用就保留; 不再被引用时登记随事务删除。
- 删除的副作用由 `MetadataRemoval` 承担: 数据库先行、文件随后。反过来的顺序会让条目指向不存在的文件, 而这个顺序最坏只留下一个无主文件。文件系统经 `ResourceFiles` 这个 seam 注入, 生产接资源库, 测试接内存实现, 顺序不变量因此不由调用方复述。

## 运行时替换

热配置变更不重启进程, 也不重建 `Runtime`: 三项分别就地生效 —— 并发上限调整任务服务的信号量凭证, 来源顺序重排登记表内部列表, 请求超时重建共享的 HTTP 客户端。整体配置存于 `ArcSwap`, 读方拿到的是完整快照。保存请求经互斥锁串行应用, 比较与生效基于同一次取得的快照。

顺序约束: 限速器必须先于 HTTP 客户端构造 (`WebClient::new` 接受 `RateLimiters`, 颠倒无法通过编译), 来源登记表必须先于爬虫工厂。客户端与限速器见 [network.md](network.md)。

## 传输契约

- 端点全部注册在 `/api` 下, 前端与 Docker 部署共用同一份契约。
- 访问令牌非空时校验 `Authorization: Bearer <token>`, 只作用于 `/api`; 静态文件不校验。
- 错误响应统一为 `{ "code": ..., "message": ... }`, 由 `ApiError` 映射到状态码; 仓储错误在映射时记录日志, 响应体不携带内部细节。查询参数与请求体都经自定义提取器, 解析失败同样走这一形状 (`invalid_query` / `invalid_body`): 框架默认的纯文本 400 会让界面无法取得错误码。配置的保存请求体是 `UpdateConfigRequest` 而不是领域类型, 且每个字段都必填 —— 缺字段用默认值补齐, 等于把用户没提交的设置重置掉。
- `AMANE_UI_DIR` (默认 `ui/dist`) 存在 `index.html` 时, 同端口提供前端产物: 命中文件按扩展名返回, 未命中回退到 `index.html` 并返回 200, 使单页应用的深链接可直接打开。越界路径不读库外文件, 一并回退到入口页。不使用 `ServeDir::not_found_service` — 它保留 404, 只适用于自定义错误页。
- OpenAPI 由 `utoipa` 编译期生成, `--print-openapi` 输出到标准输出; 版本号取自 `CARGO_PKG_VERSION`。
- 每个请求 (含静态文件) 在 INFO 级别记录方法、路径、状态码与耗时; 日志层挂在最外层, 否则「哪个页面慢」无从判断。只记路径不记查询串: 桌面外壳用 `?token=` 传令牌, 记下查询串等于把令牌写进日志。上游请求同样记录 URL、状态与耗时, 来源标识挂在 span 上, 慢请求可按来源统计。

## 媒体库扫描

- 归类优先级固定: 系统产物 → 黑名单 → 大小阈值 → 扩展名。黑名单先于大小判定, 否则大于阈值却命中黑名单的文件会被当成正常媒体放行; 命中的规则原文写进 `detail`, 界面据此说明「为什么被挑出来」。
- 扩展名不匹配任何规则的文件归入「未识别」单列一档, 不静默消失; 子树里没有媒体文件的目录记为「残留目录」, 只报真正的空叶, 含媒体的祖先不算。
- `.amane_trash` 目录整个子树剪枝, 交给清理切片; `.strm` 是路径指针, 算媒体入口但大小过滤对它无意义。
- 扫描是任务 (`TaskKind::Scan`), 不在登记请求里同步执行: 大目录的遍历是纯阻塞 IO, 处理函数放进阻塞线程池, 不占异步工作线程。
- 登记时校验路径的是 `LibraryRepository::register` 而不是端点: 存在性、是否目录、可读性与规范化都属于「登记」这件事, 走 `tokio::fs` 因而不占异步工作线程。`insert` 只写登记行, 供已校验的路径使用。
- 索引按根目录整体替换并与增量比较放在同一事务里: 中途失败不会留下半个库的索引; 路径集合用 `BTreeSet`, 两次扫描的日志顺序稳定。
- 扫描规则 (扩展名、阈值、黑名单) 在每次扫描开始时从配置快照编译: 热配置改动不需要通知处理器, 下一次扫描自然生效; 非法正则在配置提交时就被拒绝, 不等扫描才发现。

## 路径模板与整理预览

- 模板语法: `{name}` 占位符、`{name|k=v,k=v}` 值映射 (`|k=` 与 `{name|=缺省}` 把空源映成缺省)、`[...]` 可选组与 `[[...]]` 包裹组。占位符白名单在**解析期**校验, 拼错的变量在保存配置时报错, 不等渲染才变成 Unknown。
- 可选组的折叠只看**直接**子占位符, 嵌套组各自判断, 不并入外层; 组内有任一非空值即整组渲染。
- 锚 (前导 `/` 或盘符) 从**模板源**判断而不是渲染结果: 相对模板 `{maker}/…` 在 maker 为空时渲染出前导 `/`, 若据此保留锚, 空目录段会悄悄变成根目录。
- 段规范化按 Windows 创建结果对齐: 控制字符替换为空格、`/\:*?"<>|` 清洗、段尾 `.` 与空格剥除 (Windows 创建时静默丢弃, 记录与磁盘才会一致)、空段丢弃; 长字段与超长段按 UTF-8 字节截断并带省略号, 不切多字节字符。
- 预览装配只有一个入口 `PreviewAssembler`: HTTP 端点与整理任务交出同一组仓储, 拿回同一个 `OrganizePreview`。取文件、提番号、查条目、读登记都在这一个模块里。
- 渲染本身是纯函数 (`build_preview`): 文件按文件名提取番号, 条目缺席时以番号参与渲染; 提取不出番号的由装配层计入 `unmatched` 不进列表。判定顺序: 源与目标相同 → 整理登记占用 (同名不同番号) → 磁盘已存在。不创建目录、不移动文件, 重复预览结果一致。
- 整理登记 (`organize_plan`) 以 `UNIQUE(root_id, path)` 保证同库同路径只允许一个番号占用; 「同名不同番号」冲突由它判定, 写入发生在执行切片, 预览只读。
- 预览把「索引里有但磁盘上没有」的源计入 `stale` 而不是报冲突: 整理执行后索引必然落后于磁盘, 不区分就会把已整理的文件误报成目标已存在。

## 整理执行

- 执行是任务 (`TaskKind::Organize`): 处理函数与预览走同一套配对与渲染, 目标路径一致由「同一份输入 + 同一函数」保证, 不信任客户端提交的目标路径。
- 冲突处置来自预览阶段的选择 (`skip` / `overwrite` / `rename`), 冲突项没有明确选择时按跳过处理 —— 缺省路径必须是「不动文件」, 绝不能是「默默覆盖」。
- 覆盖前旧目标移入库内 `.amane_trash/<原相对路径>`: 保留相对结构, 误删可恢复; 清理切片复用同一目录。
- 改名在 `execute_item` 内部挑空闲后缀 (stem 追加 `-1`、`-2`…), 调用方只给原始目标; 后缀计算与执行分离会让两者读到不同的磁盘状态。
- 字幕按扩展名随配 (同目录、不递归), 重命名为 `<目标主干><原扩展名>`; 目标字幕已存在时保留原地, 任何字幕都不覆盖文件。
- STRM 正文是视频的完整绝对路径, 原样写出: 不经过模板的折叠与截断 —— 折叠是对路径段字面值的规则, 指针文件指向的是真实位置。
- 单项失败只跳过并记录, 不中断其余文件; 成功与跳过在任务日志里分开成行, 汇总行给出三种计数 (移动 / 跳过 / 登记)。
- 成功项逐条写入 `organize_plan`; 登记路径被占用只告警不回滚移动 —— 文件已在新位置, 登记缺失只影响冲突判定。

## 清理与回收

- 清单与执行分离: `GET /api/libraries/{id}/cleanup` 只读列出待删文件、大小与命中原因; 执行派生 `TaskKind::Cleanup`。清单为空时任务不动任何文件, 也不创建回收目录。
- 清理范围只含扫描索引里的无效文件与系统产物; 媒体与残留目录不属于清理。命中原因沿用扫描时的 `rule`/`detail` (黑名单模式原文、大小阈值), 界面据此说明「为什么删它」。
- 执行时清单重建而非复用请求参数: 界面看到的清单与任务删掉的内容来自同一张索引, 中途的扫描变化不会造成「看到 A 删了 B」。
- 文件进入 `.amane_trash/<原相对路径>` (与覆盖旧目标同一目录同一规则); 原路径不再存在, 索引条目同步删除, 磁盘与索引不脱节。
- 恢复按原相对路径反向移动; 目标已存在时拒绝 (409) 而不是覆盖 —— 回收目录里的文件保持原样, 用户处理完原路径可以重试。恢复成功的文件按「未识别」重新登记进扫描索引: 原始归类已随清理删除, 重新扫描会重新归类。
- 恢复请求拒绝包含 `..` 的路径: 回收目录的相对路径直接拼进文件系统访问, 遍历防御在端点层做。
- 回收目录的占用 (逐文件大小与合计) 由遍历 `.amane_trash` 现算, 不另存账本 —— 目录内容就是事实本身, 缓存一份只会在直接删文件时说谎。

## 配置

冷热两层分离: 冷配置 (数据目录、监听地址、令牌) 修改后需重启; 热配置 (并发、超时、启用来源) 由运行时重建生效。配置 schema 由 `schemars` 从同一份类型生成, `x-widget` 等表单提示写在字段属性上, 前端按 schema 渲染表单。
